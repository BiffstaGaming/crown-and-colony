## 1. How it works (plain English)

All the game's rule numbers — what each terrain produces, how hard it is to cross, what can be built where — come from a data file, not from code. We use FreeCol's "classic" rules file unchanged: it's the community's careful reconstruction of the original 1994 game's numbers. Because rules are data, the planned Australia variant is mostly "write a different data file."

**Worked example:** the rules file says plains cost 3 movement to enter, take 3 turns to plough, and yield 5 grain when farmed. Our code reads those numbers; it never hard-codes them.

The same "rules are data" principle applies to a unit's *capabilities* — its `<ability>` tags. The rules file is what says a caravel sails the sea, a free colonist can found a town, a privateer is a pirate, and a treasure train carries gold. Our code reads those flags from the file and asks "does this unit have ability X?"; it does not bake "the caravel is a ship" into the program. So a variant could, for instance, make a new unit found colonies just by adding one line to its data — no code change. (Six such capabilities now work this way — see Detailed rules; the rest are being migrated over time.)

The same applies to a **building's** capabilities. The rules file is what says the docks let colonists fish the sea, the custom house auto-sells goods, a church can ordain a missionary, a drydock repairs ships, a fort bombards passing enemy ships, and a schoolhouse can teach. Our code asks "does this building have ability X?" and reads the answer from the file rather than having "the docks let you fish" written into the program — so a variant could give a brand-new building any of those powers just by editing data. (Six building capabilities now work this way — see Detailed rules.)

The same goes for the **combat bonuses and penalties** that aren't tied to any one unit — the "+50% for attacking", "−33%/−66% for having little movement left", the amphibious-landing and artillery-in-the-open penalties, the "+100% for artillery defending a town against a raid", the fortified bonus, and the "−12.5% per cargo slot a ship is carrying". The rules file lists each of these as a percentage; our combat maths reads them from the file instead of having the numbers written into the code. The classic numbers are unchanged, so battles play out exactly as before — but a variant could make, say, attacking weaker or fortification stronger purely by editing the data. (If the file leaves one out, the code falls back to the classic value, so an incomplete variant still works.)

The same again for a handful of **colony economy numbers** that used to be written into the code: how much food one colonist eats each turn (2), how much surplus food a colony must bank to grow a new colonist (200), how many "liberty" points one rebel colonist is worth (200, the divisor behind the Sons-of-Liberty bar), and how much of a good a custom house keeps back before auto-selling the rest (50). These are the classic numbers, so colonies grow, starve, and rebel exactly as before — but a variant could make colonists hungrier or growth faster just by editing the data. (Again, any number left out falls back to its classic value.)

## 2. Detailed rules

- The classic ruleset defines **23 terrain types**: 8 base land, 8 forest variants, hills, mountains, arctic, and 4 water types (ocean, lake, high seas, great river).
- Flags: `is-forest`, `is-water`, `is-elevation`, `can-settle` (default true; false for mountains and all water), `is-connected` (high-seas access: true for ocean/high seas; **false for great rivers and lakes**).
- Every type has `basic-move-cost` (3/6/9 scale; 3 = one normal move) and `basic-work-turns`.
- Production entries: one `unattended` (colony-centre yield), plus attended options per goods type.
- **Unit abilities are data, consulted by id.** Every `<ability>` a unit type declares is parsed (resolved down the `extends` chain, nearest wins, explicit `value="false"` honoured, absent `value` defaults to true) into a map and asked via `UnitType.HasAbility("model.ability.X")` — exactly FreeCol's `hasAbility`. Six capabilities are now read this way instead of from a hardcoded flag: `navalUnit` (`IsNaval`), `foundColony` (`CanFoundColony`), `captureGoods` (`CaptureGoods`), `piracy` (`Piracy`), `carryTreasure` (`CarryTreasure`), `expertScout` (`ExpertScout`). The classic resolved values are unchanged — caravel naval, free colonist/seasoned scout found, frigate/man-o-war/privateer raid cargo, privateer also pirate, treasure train carries treasure, seasoned scout is the expert scout. (Other unit abilities — `person`, the combat-outcome flags `disposeOnCombatLoss`/`canBeCaptured`/`captureUnits`/`captureEquipment`/`disposeOnAllEquipLost`/`demoteOnAllEquipLost`/`bombard` — still resolve into their own named fields for now; they can migrate to the same map incrementally.)
- **Building abilities are data, consulted by id (`86d3drpgg`).** Likewise every `<ability>` a *building* type declares is parsed (same `extends`-chain resolution) into a map and asked via `BuildingType.HasAbility("model.ability.X")`. Six building capabilities are now read this way instead of from six dedicated parsed flags: `repairUnits` (`RepairsNavalUnits`), `bombardShips` (`BombardsShips`), `export` (`GrantsExport`), `dressMissionary` (`DressesMissionary`), `produceInWater` (`ProducesInWater`), `teach` (`Teaches`). The classic resolved values are unchanged — the drydock/shipyard repair ships, the fort/fortress bombard, the custom house auto-exports, the church/cathedral (not the chapel) ordain missionaries, the docks/drydock/shipyard let colonists fish, and the schoolhouse/college/university teach. (The scoped `model.ability.build` lands in the same map but keeps its dedicated scope collectors; the build-gating `required-ability` map and the modifier-derived flags — `DefenceBonus`/`WarehouseStorage`/`BellBonus`/`BreedingDivisor`/… — are a separate mechanism and unchanged.)

**Deviations from FreeCol:** none — the file is used verbatim.

## 3. Technical design

- `Ruleset.LoadEmbedded(resource)` reads a `specification.xml` **embedded in GameLogic.dll** (identical bytes for game, tests, CI); `Ruleset.LoadClassic()` is the convenience for the classic variant. Which spec loads is chosen by the selected **game variant** (`GameVariant.LoadRuleset`, ADR-018 — see [game-modes](game-modes.md)). `Ruleset.Load(Stream)` parses any spec — the engine is variant-agnostic.
- Parse: `System.Xml.Linq`; strict — missing ids/costs or duplicate ids throw `RulesetFormatException`.
- Model: `TerrainType` (immutable record; `ShortName` strips the `model.tile.` prefix), `ProductionEntry`, `GoodsOutput`. Lookup via `Ruleset.Terrain(id)` (throws `KeyNotFoundException` on unknown id).
- **Data-driven unit abilities (`86d3drpgg`):** `Ruleset.CollectAbilitiesUpChain` walks a unit type's `<ability>` elements down the `extends` chain into `UnitType.Abilities` (id → bool; nearest leaf→root definition wins, absent `value` ⇒ true), mirroring the existing `CollectRequiredAbilitiesUpChain`/`RoleType.GrantedAbilities` pattern. `UnitType.HasAbility(id)` is `Abilities.GetValueOrDefault(id)` (false when undeclared) — FreeCol `FreeColObject.hasAbility`. The convenience properties `IsNaval`/`CanFoundColony`/`CaptureGoods`/`Piracy`/`CarryTreasure`/`ExpertScout` are now computed from `HasAbility(...)` rather than parsed into dedicated record fields, so all existing call sites are unchanged. For a simple unscoped ability this yields byte-identical results to the previous per-ability `ResolveAbility` parse (verified by the full L1/L2 suite). `ResolveAbility` remains for the not-yet-migrated unit abilities (`person`, the combat-outcome flags, `bombard`). Scoped abilities (e.g. `model.ability.build`) also land in the map keyed by id, but their scope handling stays in the dedicated `CollectBuildUnitTypeScopes`/`GrantsNavalBuildScope` collectors.
- **Data-driven building abilities (`86d3drpgg`):** the same `Ruleset.CollectAbilitiesUpChain` collector now also walks a *building* type's `<ability>` elements down its `extends` chain into `BuildingType.Abilities` (id → bool), consulted via `BuildingType.HasAbility(id)` = `(Abilities ?? empty).GetValueOrDefault(id)` (false when undeclared) — FreeCol `FreeColObject.hasAbility`. Six convenience properties — `RepairsNavalUnits` (`model.ability.repairUnits`), `BombardsShips` (`bombardShips`), `GrantsExport` (`export`), `DressesMissionary` (`dressMissionary`), `ProducesInWater` (`produceInWater`), `Teaches` (`teach`) — are now **computed** off `HasAbility(...)` rather than parsed into six dedicated record fields by six separate `ResolveAbility` calls. Every call site (`Game.ColonyDressesMissionary`/`RepairsNavalUnits`/`ProducesInWater`/`GrantsExport`/the `BombardsShips`/`Teaches` reads, `SaveGame.Restore`'s water-work gate) is unchanged because the property names/semantics are preserved. For a simple unscoped ability the collector's leaf→root nearest-wins resolution is exactly what each `ResolveAbility` returned, so the classic result is byte-identical (pinned by the 14-row `DataDrivenBuildingAbilities_MatchClassicValues` theory + the full L1/L2 suite). The scoped `model.ability.build` lands in the map too, but `BuildableUnitTypeIds`/`BuildsNavalUnits` keep their dedicated `CollectBuildUnitTypeScopes`/`GrantsNavalBuildScope` collectors; the build-gating `required-ability` (`RequiredAbilities`/`CollectRequiredAbilitiesUpChain`) is a separate, unchanged map.
- **Data-driven combat modifiers (`86d3drpgg`):** `Ruleset.ParseCombatModifiers` reads the spec's top-level `<modifiers>` section (the unattached `GENERAL_COMBAT_INDEX = 50` situational bonuses, FreeCol's `Specification.getModifiers`) into a `Combat.CombatModifiers` record exposed as `Ruleset.CombatModifiers`. Eight modifiers are wired: `attackBonus` (+50), `smallMovementPenalty`/`bigMovementPenalty` (−33/−66), `amphibiousAttack` (−75), `artilleryInTheOpen` (−75), `artilleryAgainstRaid` (+100), `fortified` (+50), `cargoPenalty` (−12.5). Each spec `value` (a percentage) is divided by 100 into the fraction the combat model multiplies by, so `CombatModel.AttackPower`/`DefencePower`'s arithmetic is unchanged. The parser falls back per-modifier to `CombatModifiers.Classic` (the hardcoded classic fractions) when a modifier — or the whole `<modifiers>` section — is absent, so the default classic game is byte-identical (last definition wins on a duplicate id, mirroring FreeCol's add order). `CombatModel.AttackPower`/`DefencePower` gain a `CombatModifiers` overload; the no-arg overloads delegate with `CombatModifiers.Classic` so existing call sites (and the pure-model tests) are unchanged, and `Game`'s combat paths pass `Ruleset.CombatModifiers`. **Not wired (deliberately, with reasons):** the `colonyGoodsParty` and `shipTradePenalty` modifiers are *instantiated-on-the-fly templates* (they carry `duration`/`increment` or are built from a game option per application — not a single constant); `model.goods.bells`/`model.goods.food` etc. are zero/additive goods modifiers consumed elsewhere; and the per-unit/terrain/building combat modifiers (`offence`/`defence`/the terrain defence bonus / the colony fortification bonus / role offence-defence / the ambush bonus, which *is* the defender's parsed terrain bonus) were already data-driven via their own parsers — only the spec's *unattached* combat constants were still hardcoded, and those are what this slice routes.
- **Data-driven colony/production scalars (`86d3drpgg`):** `Ruleset.ParseColonyConstants(root, units)` reads four colony-economy constants into a `Specification.ColonyConstants` record exposed as `Ruleset.ColonyConstants` (the colony-economy analogue of `Ruleset.GameOptions`). Sources, each FreeCol-faithful: **`FoodPerColonist`** (classic **2**) ← the free colonist's `<consumes id="model.goods.food">`, resolved up the `extends` chain to the abstract `colonist` base where the value lives (mirroring FreeCol `UnitType.getConsumptionOf(food)` via the new `ResolveConsumes` helper); **`FoodForGrowth`** (classic **200**) ← the free colonist's `<required-goods id="model.goods.food">` (already parsed onto `UnitType.BuildCost`; the spec mirror of FreeCol's `Settlement.FOOD_PER_COLONIST`); **`LibertyPerRebel`** (classic **200**, FreeCol `Colony.LIBERTY_PER_REBEL`) and **`DefaultExportLevel`** (classic **50**, FreeCol `ExportData.EXPORT_LEVEL_DEFAULT`) ← model-code constants with no spec element, so they take the `ColonyConstants.ClassicDefaults` value (data-overridable for a variant). Each missing source falls back to its classic default, so the default classic game is byte-identical (`Ruleset.ColonyConstants` for the classic spec equals `ColonyConstants.ClassicDefaults`). **Routing:** the food pair is read by `Game` (which holds the ruleset) in the colony turn (`RunColonyTurn` consumption + the 200-food growth step) and the net-food oracles (`ColonyNetProduction`/`ColonyNetFood`/the worker planner). The liberty/export pair is carried *onto each colony* as a plain value — `Colony.RebelLibertyDivisor` (the `SonsOfLiberty` divisor + the 100%-SoL liberty cap) and `Colony.ExportRetainDefault` (the `ExportOf`/`SetExport` default) — set from the ruleset when a colony is founded (`Game.FoundColony`) or loaded (`SaveGame.Restore`), exactly the existing `Colony.Government` precedent (the pure colony model has no ruleset reference). The former `Colony.FoodPerColonist`/`FoodForGrowth`/`LibertyPerRebel`/`DefaultExportLevel` constants are kept as `static readonly` aliases of `ColonyConstants.ClassicDefaults` so presentation/test static reads (e.g. the colony panel's `Food: x/200` label) keep the classic figure unchanged.
- The copied spec file is upstream data — never edit (see `game/data/README.md`); deviations happen in code or future overlay rulesets.
