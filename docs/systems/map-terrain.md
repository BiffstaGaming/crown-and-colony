## 1. How it works (plain English)

The world is a rectangular grid of square tiles, each with one terrain type from the rules data. For now the map is a placeholder: a 2-tile ocean border around one landmass whose terrain is randomly scattered (but always the same for the same game seed). On screen each terrain is a flat colour — ocean blue, plains tan, forests green, mountains grey.

**What the player sees and does:** the coloured map; pan with middle/right-mouse drag, zoom with the wheel.

**The high seas.** The deep water along the far east and west of the map is the **high seas** — the open ocean a ship sails into to reach Europe. It isn't a fixed strip of columns: the game looks at how far each edge-water tile is from the nearest land and marks the genuinely open water (a few tiles clear of any coast) as high seas, so the high-seas line hugs the shape of the coastline. There's always at least one high-seas tile on each side so a ship can always find a way out.

**Mountains & hills look like ranges.** Elevated terrain isn't sprinkled tile-by-tile any more. Instead the game grows **ranges**, just like the original: it picks a few starting spots on the land, then walks in a straight-ish direction laying down a chain of mountains, dropping hills (and the odd extra mountain) on the tiles right beside the chain. The result reads as ridgelines snaking across a continent, not random grey dots. After the ranges are laid, a handful of stray hills and mountains are still scattered here and there for variety. A bigger map (or more land) gets proportionally more elevation, so a small world isn't crammed with mountains and a huge one isn't bare. As always, the same seed makes the same ranges every time.

**Choosing the world (new game).** When you start a new game the menu first asks two things: the **world size** (Small 30×20, Standard 36×24, Large 56×38, Huge 80×52) and how much of it is **land** (Sparse 30%, Normal 45%, Dense 50%). A bigger map gives more room to expand and explore; more land means larger continents and less sea. Leave them on the defaults (Standard / Normal) and you get exactly the world the game has always generated. The same seed plus the same two choices always makes the same world.

**Choosing the shape of the land (new game).** You can also pick the **landmass style** — the same choice the original game and FreeCol offer:

- **Continent** (the default): one big main landmass, the world the game has always made.
- **Archipelago**: a handful of large islands separated by sea — a few sizeable bodies of land you sail between.
- **Islands**: lots of smaller islands scattered across the ocean, so almost every colony is coastal.

The style only changes *where the land is*; everything else (climate, mountains, rivers, fish, resources, the high seas) is laid on top exactly the same way. Leave it on **Continent** and the world is byte-for-byte the one the game always generated. As ever, the same seed plus the same choices makes the same world every time, on every machine. (When you play the fixed America map, the style is ignored — that map's coastlines are already drawn.)

**Playing on the real America.** As well as a freshly-generated random world, you can choose to play on the **fixed map of the Americas** — the same hand-drawn New World map that ships with FreeCol (a tall north-to-south strip of the two American continents, 40 tiles wide by 180 tall). Its coastlines and mountains are exactly where the map's author drew them, so the same continents appear every time. We take only the *land shape* from that map; the game still lays its own rivers, fish, mineral deposits, native villages and your starting position on top, so each America game still differs by seed (a different river here, a different silver lode there) while the continents stay put. On the random-world option the world-size and land-mass choices apply as before; on the America option they're ignored (the map is a fixed size).

**Loading a hand-made map (importing).** Behind the fixed America map sits a small **map importer**: it reads a plain-text map description and turns it into a playable world. A description is just a grid of terrain names (which is all the America map uses), and it can *optionally* spell out extra things on specific tiles — a **mineral deposit** or other bonus here, a **river or road** there, a **lost-city rumour** to explore, and **native villages** (which tribe, how big, whether it's the tribe's capital, and what skill it teaches). The America map deliberately leaves all of that out (so the game lays its own, as described above), but the importer can read a map that *does* include them — handy later for a hand-crafted scenario or the planned Australia variant, where you'd want specific villages and resources placed by hand rather than scattered randomly. We ship a tiny **example map** that uses every one of these extras, purely to demonstrate and test the format. The importer reads the things the game already knows how to do; a few rarer bits of a full FreeCol save (European colonies, exact starting ships, river bends drawn just so) are left for later — see the technical notes for the exact supported list.

**Reading an original Colonization map file (`.MP`).** The importer can also read the **binary map files of the original 1994 game** — the `.MP` files its map editor produced (and that fan sites still share). Those files carry much less than our text format: just the terrain of each tile (including hills and mountains) and whether a minor or major river runs across it — no bonus resources, no villages, no starting positions. That is *exactly* what FreeCol's own `.MP` reader extracts, and we read the same subset: the land comes out of the file, and the game lays its own resources, rumours, villages and your landing spot on top, just like the fixed America map. (We never ship any original-game file ourselves — that data is copyrighted; the reader exists so a player who owns one can import it.)

**When a hand-made map places the villages.** If an imported map *does* spell out native villages, the game now **uses exactly those** — at the tiles, tribes, sizes, capital flags and taught skills the map author chose — and **does not** scatter its own randomly on that map. (Each imported village still claims the land around it and joins the trade economy just like a generated one, and its tribe joins the game as a player.) When the map says *nothing* about villages — which is the case for the shipped America map and for every randomly-generated world — the game places villages itself, exactly as before. So a map either hands you its hand-placed natives or lets the game generate them; the default America and random games are completely unchanged.

**When a hand-made map fixes where you start.** A scenario map can also pin down two more things, both optional. First, **where you land**: instead of the game choosing a coastal spot for you, the map can name the exact tile your colonists land on (and, separately, the tile the King's army arrives at if you declare independence). Second, the **named regions**: instead of the game working the regions out from the terrain, the map can carry its own ready-made region layout (every tile already tagged with which region it's in). Both are extras a scenario author would use to hand-craft a specific opening — "you start *here*, in *this* named land." A map that says nothing about either (the shipped America map, every random world) is completely unchanged: the game picks your coastal start and works out the regions itself, exactly as before.

**Naming the New World.** The first time your explorers set foot on the new continent — the moment a land unit steps ashore (or your colonists disembark from the caravel) — the game asks you to **name the new land**, exactly as the original does. A small box appears with a suggested name ("The New World") you can keep or type over; whatever you choose is your nation's name for the continent from then on. It only ever asks once per game, and only the first time you actually touch land (sailing around offshore doesn't count). If you just hit OK without typing — or dismiss the box with Escape or its close button — you get the default name, so the game never asks again. (A ship arriving back from Europe onto open water isn't a landing — you have to actually step onto land.)

**Fishing the coast.** Open ocean yields a flat 2 fish, but water hugging the shore yields more — a **coastal** water tile (one that borders three or more land tiles) gives **4 fish** instead of 2. This is the classic "+2 fish on the coast" rule that makes a colony founded on the shoreline worth building: its sea tiles feed the town. Only fish gets the bonus, only genuinely coastal water earns it (a single far-out land tile two squares away isn't enough), and the open-sea **high seas** never get it. Worked example: a colony with one ocean tile that touches three of its land tiles can put a fisherman there for 4 food a turn instead of 2. And where a **river meets the sea**, the water beside that river mouth gets a further **+1 fish** — see [rivers-tile-improvements](rivers-tile-improvements.md).

**Clicking a tile.** Because the map is drawn as a grid of **diamonds** (not squares), working out which tile you clicked needs a little care: a click anywhere inside a diamond — right up to its slanted edges — must select *that* diamond, not the rectangle around it. The game does exactly that: it turns the click point back into map coordinates and picks the diamond it falls inside, so clicks near a tile's pointed corners land on the right tile rather than a neighbour. The pick uses the **click's own position** (where the button actually went down) rather than wherever the cursor happens to be a moment later, so a click stays accurate even while the map is being panned or zoomed — fixing the old "clicks land on the wrong tile or miss" wonkiness (`86d3f675b`).

**Regions.** Behind the scenes the map is also carved into named *regions*, exactly as the original game does. The frozen top and bottom rows are the **arctic** and **antarctic**; the western sea is the **Pacific** and the eastern sea the **Atlantic**, each split into a north and south half; every separate continent is its own **land region** (a very big one is chopped into ~75-tile pieces so no single region swallows a whole continent); runs of hills and mountains become **mountain regions**; **each river is its own region too** — the first explorer to walk its banks discovers and names it ("River 1", "River 2", …) and earns a few points for it, bigger rivers being worth more; and any pond or inland sea with no water route out to the open ocean is recognised as a **lake** rather than ocean. Every tile belongs to exactly one region. Each region carries a *score* — the points a player earns for discovering it (a faraway sea like the Pacific is worth more; bigger land regions are worth more). The map also quietly keeps **nine "compass boxes"** — north-west through south-east ninths of wherever the land actually is — which the original uses to decide roughly where each native tribe should live (our village placement doesn't read them yet; they're in place for it). Regions are computed purely from the finished terrain, so the same map always produces the same regions, on every machine.

## 2. Detailed rules

- Coordinates: (0,0) top-left; X east, Y south. Diagonals count as adjacent (8 neighbours), as in the original game.
- Same seed → identical map, every time, every machine (ADR-009).
- **Climate-band generation (Phase 2a):** a continent grown from seeded blobs (a configurable land fraction — default 45% — with watery margins); per-tile climate triple — temperature from latitude (40 °C equator → −20 °C poles, jittered), humidity from smoothed noise (0–100), and a **lowland** altitude (1–3) — hills and mountains are no longer scattered per-tile here (see the range pass below); terrain picked among ruleset types whose `<gen>` envelope contains the triple (forest-vs-clear is a separate ~45% roll; off-envelope triples take the climate-nearest type). The open-sea **route to Europe (high seas)** is a band hugging the east/west edges: a near-edge ocean tile becomes high seas when there is no land within a few tiles of it, so the high-seas line follows the coastline's distance rather than sitting on fixed columns.
- Result: hot wet equator → savannah/tropical forest, dry bands → desert/scrub, poles → arctic/tundra/boreal.

**Mountain & hill ranges (`86d3c9w71`).** After the climate terrain is laid, `MapGenerator.MakeMountains` grows elevation as **ranges** by a directional walk, faithful to FreeCol `TerrainGenerator.createMountains`. Two passes over the land: (1) **ranges** — until a tile budget of `½ · landCount / mountainNumber` (FreeCol `randomHillsRatio = 0.5`, `mountainNumber = 10` → ≈5% of land) is met, take the next shuffled non-elevation land tile, pick a random walk direction and a length `maxLength − rand(maxLength/2)` (`maxLength = max(w,h)/10`), and step that many land tiles laying a mountain at each step plus, on each step tile's 8 land neighbours, a mountain (2/8), a hill (5/8) or nothing (1/8); the walk stops at water or the map edge. (2) **sprinkle** — the other half of the budget (≈5% of land) is scattered as 25% mountains / 75% hills ("random hills here and there"). So elevation reads as ridgelines, and the total elevation share (~10% of land) scales with both map size and land fraction. **Bonus resources are placed last** (after the range pass *and* the high-seas reclassification), faithful to FreeCol's "add bonuses only after the map is completed, otherwise we risk creating resources on fields where they do not belong (like tobacco on hills)" — so a tile retyped to mountains carries mountain resources (ore/silver), never the lowland resource it might otherwise have rolled.

**Tunable counts & climate at New Game (`86d3fq18b` / `86d3fq13u`).** The four density numbers above — `mountainNumber` (elevation per N land tiles; higher = fewer), `riverNumber` (river budget as a % of allowed land), `forestChance` (the forest-vs-clear roll), `bonusNumber` (the land-bonus chance) — are no longer hardcoded: they live on a **`MapGenerationOptions`** record whose `Classic` singleton holds the historical values (mountain 10, river 15, forest 0.45, bonus 0.10), and a new game can dial each up or down (the New-Game dialog offers Few/Normal/Many style presets). The same record also carries two **climate bands** mirroring FreeCol's `model.option.temperature`/`humidity`: a **temperature bias** (degrees added to every tile's latitude temperature) and a **humidity bias** (added to the smoothed humidity), each an RNG-free offset applied *after* the existing climate draws and clamped to the spec envelope — so a warmer/wetter setting just re-picks terrain from a shifted climate (more desert/jungle when hot, more marsh/tundra when cold) without changing the random draw sequence. Leaving every dial at its default (`Classic` + zero bias) reproduces the historical map **byte-for-byte**; changing a count changes how many elevation/river/forest/bonus rolls happen, which deterministically changes the map for a given seed.

**Landmass styles (`86d3drn76`).** The **shape** the land takes on a generated map is a new-game option — FreeCol's `model.option.landGeneratorType` (`LandGeneratorType`). `LandStyle` (enum `Continent=0`/`Archipelago=1`/`Islands=2`) mirrors FreeCol's `LAND_GENERATOR_CONTINENT/ARCHIPELAGO/ISLANDS`; `MapGenerator.Generate` and `Game.New` take an optional `landStyle` (default `Continent`). **`Continent` routes through the unchanged `GrowContinent` blob-grower**, so a default-styled call draws the identical RNG sequence and produces a **byte-identical** map (ADR-009) — the default game, goldens and soak baseline are untouched. `Archipelago` and `Islands` instead call `GrowSeparateMasses`, a faithful port of FreeCol `LandMap.generate`: each island is a connected blob grown by `AddLandMass` (FreeCol `LandMap.addLandMass`) from a fresh sea seed that has no land neighbour, so the masses stay unconnected. **Archipelago** lays 5 large islands at ≈10% of the land budget each (`archsize = targetLand·10/100`, size `archsize±5`) then falls through to the islands fill; **Islands** keeps adding 25..75-tile islands (`25 + rand(50)`) until the land budget is met. The land stage is the *only* style-dependent step — climate, mountains, high seas, rivers, resources and regions are the shared pipeline, applied identically to whatever land shape results. *Faithful-subset deviations:* FreeCol's `LandMap` additionally forces polar land along the top/bottom rows (`addPolarRegions`) and deletes 1×1 islets (`cleanMap`); we keep the poles as open sea (our polar terrain is climate/region-derived, not forced land) and rely on per-island connected growth (single-tile islets are already rare). FreeCol's `distanceToEdge`-scaled edge clearance is replaced by our fixed `LandMarginX=4`/`LandMarginY=2` margin, so every style satisfies the same high-seas-band invariant the downstream passes assume. The non-default styles **draw the same number/kind of RNG calls only on their own land stage** — they do not touch stream 0's later (economy/turn) sequence beyond the land draw, exactly as `landMass` already does. No save change (land shape persists as terrain ids, like world size).

**World-size & land-mass options (`86d3c9w9c`).** Map width/height and the land fraction are **new-game options** (FreeCol's `model.option.mapWidth`/`mapHeight`/`landMass`). `MapGenerator.Generate` takes a `landMassFraction` (the share of tiles grown into land); `Game.New` takes `mapWidth`/`mapHeight`/`landMassFraction`. The offered presets live in `WorldSizeOptions` ("data not code", like the game variants): sizes Small 30×20 / Standard 36×24 / Large 56×38 / Huge 80×52, land Sparse 30% / Normal 45% / Dense 50% — bounds mirror FreeCol (width 30–200, height 20–200, land 15–50%). **The defaults equal the shipped world (36×24, 45%)**, and the default-valued call uses the identical arithmetic as before, so a default new game is **byte-identical** (ADR-009) — the visual goldens and soak baseline are untouched; only a *non-default* choice changes the map. The land fraction only sets how many tiles `GrowContinent` grows (the per-tile RNG draw order is unchanged), so a non-default world is still fully determined by `(seed, width, height, landMass)`.

**High-seas band (86d3c9w8b).** Faithful to FreeCol `Map.resetHighSeas`: after terrain is laid, each row's contiguous ocean strip up to 10 columns in from the east/west edge is examined, and an ocean tile with no land within 4 tiles (8-direction Chebyshev) is reclassified as high seas; each side keeps its furthest-from-land tile as a guaranteed exit. Replaces the former rule that fixed high seas to the two outermost columns. RNG-free, no save bump (see §3).

**Coastal fish bonus (86d3c9we8).** Faithful to FreeCol's classic `model.improvement.fishBonusLand` (an index-50 **additive +2** modifier on `model.goods.fish`, scoped `isWater && !highSeas`). A water tile's fish *potential* gains a flat **+2** when it has **more than two** adjacent land tiles — the Col1 "≥3 land neighbours ⇒ 4 fish, else 2 fish" rule, applied by FreeCol's map generator `TerrainGenerator.perhapsAddBonus` (`adjacentLand > 2`). We compute this from terrain + 8-direction adjacency at read time (no stored improvement), so it stays a pure function of the map: **high-seas** tiles are excluded (the improvement's `match-negated` scope); **lake** tiles (non-high-seas water) qualify. The bonus is added in `TileYieldPotential` after the bonus-resource modifiers, so founding-father and expert modifiers stack on top of it exactly as they do for any tile. The river-mouth `fishBonusRiver` (+1) is **now implemented** (a non-high-seas water tile adjacent to a river-mouth land tile gets a further +1 fish, stacking on the coastal +2) — see [rivers-tile-improvements](rivers-tile-improvements.md) for its rule. RNG-free, no save bump (yields are derived from terrain + the river layer + adjacency, never stored).

**Bonus resource placement (`86d3c9wbp`).** Resources are scattered in the final pass once terrain is settled (after the mountain ranges *and* the high-seas band), faithful to FreeCol `perhapsAddBonus`. A **land** tile with a resource table gets one at the **bonus-number** chance (**10%**, FreeCol `BONUS_NUMBER`). A **water** tile gets one only where it borders **more than one** land tile, at FreeCol's adjacency-scaled odds `1 / (10 − adjacentLand)` — so open ocean stays bare while a tightly-enclosed bay is richest; *which* resource is the terrain's weighted pick.

**Per-resource quantity (`86d3c9wbp`, persistence facet — v46).** Some resources are *finite*: FreeCol's `minerals`/`ore`/`silver` carry a `minimum-value`..`maximum-value` range (e.g. minerals 40–400), and a placed deposit gets a random amount in that range that depletes as it's worked. We now model and persist that quantity: each `ResourceType` parses its min/max, a placed finite deposit is rolled to a `MinValue..MaxValue` amount (a limitless resource — most of them — carries none), the `GameMap` holds a sparse `tile → quantity` layer, and the save stores it (`ResourceQuantities`, v46, omitted when none). **The roll is now run at game start** (`Game.New` calls `Game.RollResourceQuantities` right after map generation), so every placed finite deposit carries a quantity from turn 1. It rolls on a *reserved* RNG stream (102), so it shifts no stream-0 draw — the human's economy/turn sequence is byte-identical; what it *does* change is that a default save now writes a `ResourceQuantities` token, so the map golden and soak baseline were regenerated this wave. *Deviations / deferred:* FreeCol's high-seas-**connectivity** gate on water resources is still approximated by the land-neighbour rule (an enclosed lake can still draw a fish).

**Depletable resources — used up as they're worked (`86d3fpxam`).** A finite deposit doesn't last forever. Each turn a colonist works a tile that carries one (minerals/ore/silver), the deposit's quantity drops by exactly the *bonus* that resource added to that turn's output — e.g. an ore deposit on a hills tile (4 ore by itself, +2 from the deposit) loses **2** each turn it is mined. When the quantity runs out the deposit vanishes and the tile falls back to its bare yield (that hills tile keeps producing its plain 4 ore, just without the bonus). A deposit nobody works never depletes, and a limitless resource (the great majority — sugar, furs, prime grain, …) is never expended at all. Worked example: a 5-deep ore deposit mined at 2/turn reads 5 → 3 → 1 → gone (the third turn's −2 takes the last 1 below zero, so the deposit is removed). This matches FreeCol's "the silver runs out" behaviour and reuses the already-persisted quantity (no new save data).

**Clearing a forest can uncover a hidden resource (`86d3fpx99`).** When a pioneer finishes clearing a forest there's a small chance (the classic **5%**) the freshly-cleared ground turns out to hold a bonus resource — a prime field where the trees used to be. The roll only ever fires on a clear-forest (it is the only improvement that carries an expose chance) and only when the cleared tile holds no resource already; the resource that appears is drawn from whatever the *new* (cleared) terrain can host. The draw goes through the same seeded randomness everything else uses, so the same game replays identically.

**A lumber mill triples a forest-clear's lumber (`86d3fpy8x`).** Clearing a forest delivers a one-off batch of lumber (classic 20) to the colony that works the tile. If that colony has built a **lumber mill**, the delivery is tripled — 60 instead of 20 — exactly as in FreeCol. A colony with only the basic carpenter's house (or none at all) gets the plain amount.

**Deviations from original / FreeCol:** uses FreeCol's climate *data* and option *bounds* but not its exact climate algorithm; the **mountain/hill range walk now follows FreeCol `createMountains` directly** (directions, length, fringe odds, and the half-ranges/half-sprinkle split). Because the classic spec's hill/mountain `<gen>` envelopes span all latitudes, a single hill type and a single mountain type suffice at every latitude — we don't need FreeCol's per-latitude mountain/hill tile-type lists. FreeCol's `LAND_GENERATOR_TYPE` is **now implemented** as the **landmass-style** option (continent / archipelago / islands — see below); rivers are done. Square grid topology as in the 1994 original.

### Regions (86d3c9w12)

After terrain is laid down, every tile is assigned to exactly one region, in this order (earlier passes win a tile; later passes skip already-claimed tiles):

1. **Polar bands** — land in rows `[0, POLAR_HEIGHT)` is **arctic**; land in rows `[Height − POLAR_HEIGHT − 1, Height)` is **antarctic** (`POLAR_HEIGHT = 2`, so 2 top rows / 3 bottom rows — the same asymmetry FreeCol's loops produce). Polar water is left for the ocean pass. Score 0.
2. **Oceans** — a **Pacific** (west) and **Atlantic** (east), each with a **north** and **south** quadrant. Each quadrant is flood-filled (8-direction) from the first water tile down its outer column, in three escalating bounds — own quadrant, own horizontal half, the whole map — so a region can overflow into its opposite quadrant when the geography demands. Tiles live in the four leaf quadrants; the parent ocean carries the discovery score (**Pacific = 100**, Atlantic = 0, `PACIFIC_SCORE_VALUE`).
3. **Lakes** — any water the directional ocean fill cannot reach (an enclosed body with no sea route out) becomes its own score-0 **lake** region (`RegionType.Lake`), so no water tile is left unassigned. This is exactly FreeCol's `TerrainGenerator.createLakeRegions` set ("`!isLand && getRegion()==null`" after the oceans are assigned). Those tiles are then **retyped to lake *terrain*** (`model.tile.lake`, FreeCol `makeLakes` `t.setType(lakeType)`) in `MapGenerator.Generate` after region assignment — so a lake carries the lake terrain's gen-data (fish, no settle, move cost) rather than ocean's. **A great-river spine (see below) is enclosed water too, so the lake retype *skips* `model.tile.greatRiver` tiles** — they keep their own navigable-river terrain rather than becoming lake.

**Great rivers (`86d3fpx8p`, FreeCol `River.drawToMap` + `model.tile.greatRiver`).** FreeCol retypes a river *section* that reaches fjord size to the navigable `model.tile.greatRiver` water terrain (gated on the `enableGreatRivers` map option, which ships **off**). Our subset rivers carry no per-section size, so a river's accrued **length** is the proxy: when the `greatRivers` map option is on, `MapGenerator.PromoteGreatRivers` retypes the **downstream spine** (the last `GreatRiverSpineLength = 3` tiles, nearest the mouth) of every river at least `GreatRiverMinLength = 6` tiles long to `model.tile.greatRiver`, and removes the river improvement on those tiles (FreeCol: "changing the type resets the improvements"). The result is a wide navigable channel: the tiles are **water** (ships pass, land units cannot enter — `IsWater = true`) and persist via their terrain id (no new save field). The flag **defaults off** (matching FreeCol), so the default game is byte-identical; the retype is a **pure, RNG-free post-process** of the already-walked river paths, so even an enabled game keeps the same stream-0 draw sequence — only the terrain output gains great-river tiles, never a land tile's climate/elevation type. (Renders as ocean in the main view, like lake.)
4. **Mountain regions** — each contiguous block of hill/mountain (`IsElevation`) land not already in a polar band becomes one mountain region, scored `2 × tile-count`.
5. **Land regions** — each remaining contiguous landmass (8-direction) becomes one land region. A landmass larger than `LAND_REGION_MAX_SIZE = 75` is split into ~75-tile chunks (target 75, or half the remainder when it is below 150). Score = `max((int)(regionSize / totalLandTiles × 1000), 5)` (`LAND_REGIONS_SCORE_VALUE`, `LAND_REGION_MIN_SCORE`); the denominator is *all* land tiles, polar and mountain included.
6. **River regions (`86d3fpxnm`)** — each **connected river system** (8-direction over the tiles carrying the river improvement) becomes one keyless, **discoverable** `RegionType.River` region, and its tiles are **reassigned** to it — they genuinely leave their land region, exactly as FreeCol does (`TerrainGenerator.createRivers` ~L587 creates a discoverable `ServerRegion(RegionType.RIVER)` per river; `River.java:436` `region.addTile(tile)` → `ServerRegion.addTile` L203-204 re-points `tile.setRegion`). Score = `2 × Σ` of the system's per-tile river **magnitudes** (FreeCol `2 × Σ RiverSection.getSize()`). Rivers are therefore discoverable and nameable ("River 1", …) through the existing region-discovery path, and a river discovery pays its score. Appended **after** the land regions, so every pre-existing region keeps its id (only river *tiles* change region — the deliberate layer change). *Faithful-subset note:* FreeCol keys one region per river **walk**; our river identity is the finished improvement layer, so a tributary and its trunk (one connected system) share one region.
7. **Geographic thirds (`86d3fpxnm`)** — the table then appends FreeCol's nine **virtual** "geographic thirds" regions (`ServerRegion.getStandardRegions`, `server/model/ServerRegion.java` L370-472): keyed (`model.region.northWest`/`north`/`northEast`/`west`/`center`/`east`/`southWest`/`south`/`southEast`, created in that order), type Land, **score 0, never discoverable, claiming no tiles** — each carries only a **bounding box** (`Region.Bounds`, persisted omit-when-null at v69). The boxes are **land-weighted** thirds, not geometric ones: two Y delimiters split the non-polar land tiles into three equal-count horizontal bands (`findYForThirdsOfLand`), then each band gets its own two X delimiters splitting *that band's* land into equal-count column thirds (`findXForThirdsOfLand` over the band's **inclusive** row range — a delimiter row counts toward both adjacent bands, exactly as FreeCol's `subMap`), all via the verbatim `findThirdsOfValues` port. Our nine half-open boxes `[0,xD0)/[xD0,xD1)/[xD1,w)` per band `[0,yD0)/[yD0,yD1)/[yD1,h)` **partition the map exactly**; FreeCol's `ensureWithinMap` cap drops the last row/column from every box (a Java `Rectangle` artifact) — a deliberate, documented deviation. FreeCol consumes the boxes to seed **native settlement placement** (`SimpleMapGenerator` filters candidates by `getBounds().contains(x, y)`); **our native placement does not read them yet** — a documented consumer gap (`NativeSettlementGenerator` keeps its settlement-number bands).

**Determinism:** region assignment draws **no randomness** (no RNG parameter at all) — it is a pure function of the finished terrain **plus the river-improvement layer**, mirroring [native land claims](natives.md). It therefore perturbs no RNG stream (ADR-009) and recomputes byte-identically at game start and on load.

**Faithful subset / deviations:** the mountain regions are derived from the finished hill/mountain terrain (a contiguous-block scan, RNG-free), whereas FreeCol builds a `ServerRegion` *during* its `createMountains` walk; both yield the same region type and `2 × size` score, so the only difference is that our region pass runs after terrain rather than alongside the walk. (The walk itself — `MapGenerator.MakeMountains` — now matches FreeCol's range generation; see §2.) **River regions and the nine geographic-thirds boxes are now produced** (`86d3fpxnm`, steps 6-7 above). The **COAST / DESERT region types are reserved-only — and that is the faithful state**: FreeCol *declares* them (`common/model/Region.java` enum values) but its generator **never instantiates either**; our `RegionType.Coast = 5`/`Desert = 6` mirror that exactly (previous revisions of this doc called them "deferred" — corrected: there is nothing to defer). The LAKE region type **is** produced, and its tiles carry **lake terrain** (`model.tile.lake`, see step 3). Region **discovery** is implemented (P6, `86d3c9w2f` — see the Region discovery subsection above and §3): per-player discovery + naming + the exploration-score reward + a history event, and it now covers river regions too. The explorer's-map naming **UI** is still a later presentation slice; the discovery *engine state* it reads is in place.

**Save impact (no version bump).** `RegionType` serialises as its enum ordinal inside the v35 region layer, so a default map that contains an enclosed lake now writes `Type = 4` where it previously wrote `0` (Ocean). This is an existing-field **value** change, not a format/schema change (no new field), so the save version stays **45** — consistent with v35's stated design that the region layer is persisted "only so a loaded game keeps the exact ids it was played with **even if this algorithm later changes**". Pre-existing saves load their persisted region types verbatim (an old lake stays tagged Ocean); only newly-generated maps classify lakes. No loader logic branches on lake-vs-ocean, so no migration is needed.

### Region discovery (P6, `86d3c9w2f`)

When one of your units sees a new part of the map for the first time — your fog lifts over a tile in a region nobody has reached yet — you **discover** that region. The moment it happens:

- The region is **named** ("Land 1", "Mountain 1", or "Pacific Ocean") and recorded as discovered **by you**, on this turn.
- You **earn its exploration points**: a land region is worth its share of the continent (bigger = more, up to ~1000), a mountain range is worth `2 ×` its size, and the **Pacific Ocean is worth 100**. The polar ice caps, the Atlantic, and inland lakes are worth nothing and aren't "discoveries" at all.
- A line goes into your **history report**: *"Discovered Land 3."* (the same log the colony-founded and war-declared notices use).

> **Worked example.** Your caravel sails out of port into open water and lifts fog over an ocean tile. That tile belongs to the Pacific, so you discover the **Pacific Ocean** → **+100** to your score and a "Discovered Pacific Ocean." line in your history. Next turn your pioneer steps inland and reveals a new stretch of plains: you discover **Land 1** and earn that land region's score. Each region is discovered only once — the first colonial power to reach it claims it; sailing back over the same water later does nothing.

The rival European powers discover regions too (the same way you do), but those discoveries don't appear in *your* history report or score — they just mean you can't be the one to "first-discover" a region a rival already reached. Native nations never discover regions.

**What you see / do:** nothing to do — discovery is automatic as you explore. The score and the history line are the reward. (An on-map "explorer's map" naming UI is a later presentation slice; the engine state it would read is in place now.)

**Faithful-subset notes.** FreeCol awards the score only when the `EXPLORATION_POINTS` game option is on; the classic ruleset enables it, so we always award it. FreeCol names regions from per-nation name lists (with a generic "{Nation} {Type} {n}" fallback); those name lists aren't loaded yet, so we use **only the deterministic fallback** — "Land 1", "Land 2", … per (player, type), with the nation prefix when the player has a nation. This is RNG-free, so the default game stays byte-identical (ADR-009). A fixed region keeps its predefined label (the Pacific → "Pacific Ocean").

## 3. Technical design

- `Position` (record struct): adjacency + neighbour enumeration.
- `GameMap`: immutable terrain grid (row-major array), bounds checks throw off-map.
- `MapGenerator.Generate(ruleset, w, h, IGameRandom, landMassFraction = 0.45)`: pure function of its inputs; `landMassFraction` (default `MapGenerator.DefaultLandMassFraction`) is the `targetLand` ceiling in `GrowContinent` (replaces the former `0.45` literal). `Game.New(ruleset, seed, mapWidth = 36, mapHeight = 24, …, landMassFraction = 0.45)` forwards all three world-shape params. **Pipeline order:** `GrowContinent` → humidity noise → climate-terrain loop (lowland only, no per-tile elevation, no resources) → `MakeMountains` (range walk) → `ResetHighSeas`, then the **shared decorate tail** `BuildDecoratedMap(…, greatRivers = false)`: `MakeRivers` (which grows each river's **small→large magnitude** at tributary confluences via `GrowRiverMagnitudes` — RNG-free — and, when `greatRivers` is on, also retypes long-river spines to `model.tile.greatRiver` via `PromoteGreatRivers` — RNG-free) → **resource pass** → `RegionGenerator.Assign`/`GameMap.SetRegions` (no RNG) → lake retype (skips great-river tiles) → final `GameMap`. The tail is factored out of `Generate` so the fixed-map path reuses it verbatim (see `DecorateFixedMap` below) — the random default game's draw order is unchanged, so it stays byte-identical. `Generate`/`Game.New` carry a `greatRivers` flag (FreeCol's `enableGreatRivers`, **default off**), so an unpicked game is byte-identical.
- **Fixed scenario maps (America), slice A+B:** `FixedMap` (engine-free, ADR-006) loads a **terrain-only** `GameMap` from an embedded grid — FreeCol's hand-made `M_America_Mazim.fsm` (GPL v2), extracted to `game/data/maps/america.txt` (header `WIDTH HEIGHT`, then row-major terrain short-names; 40×180; provenance in `game/data/maps/PROVENANCE.md`, embedded via `GameLogic.csproj`). `MapSource` enum (`Random`/`America`); `FixedMap.TryLoad(source, ruleset)` returns the loaded terrain map for `America` and `null` for `Random` (the caller generates that), and `FixedMap.TryImport(source, ruleset)` returns the **full `MapImportResult`** (terrain + any declared settlements) for `America` (`TryLoad` is now `TryImport(...)?.Map`) — the seam `Game.New` uses so an imported map's settlements reach the game. `MapGenerator.DecorateFixedMap(terrainMap, ruleset, random)` runs the **same `BuildDecoratedMap` tail** (rivers + resources + regions + lake) on the loaded terrain, so the fixed map gains every gameplay layer a scenario file doesn't carry. `Game.New` gains `MapSource mapSource = MapSource.Random`: it calls `FixedMap.TryLoad`, and on a hit decorates that terrain (its 40×180 dimensions override the world-size args, which apply only to the random branch — the start latitude uses `map.Height`); on a miss it generates as before. **Determinism (ADR-009):** the fixed map draws rivers/resources from the same map stream, so an America game is fully determined by its seed; the default (`Random`) branch is untouched, so the soak/goldens are unchanged. *Terrain only is taken from the `.fsm`* — rivers/resources/natives/start are ours. **Presentation (slice C):** `NewGameDialog` gains a **Map** dropdown (Random / America) above the size/land/difficulty rows; picking America **disables** the size & land dropdowns (a fixed map sets its own dimensions). The choice rides `GameController.PendingMapSource` (a static surviving the menu→game scene change, like `PendingWorldSize`) into `GameController.StartNewGame(seed, size, land, difficulty, mapSource)` → `Game.New`. The parameterless `StartNewGame(seed)` (tests/goldens) passes `MapSource.Random`, so it is unchanged.
- **Faithful map importer (`86d3c9wwk`):** `MapImporter` (engine-free, ADR-006, deterministic — no RNG) generalises the terrain-only America loader into a parser of a richer map definition, mirroring FreeCol `FreeColMapLoader` (which imports a saved map's tiles with their `TileItemContainer` items — resources, rivers, lost-city rumours — and native ownership/settlements). `MapImporter.Import(TextReader, ruleset, sourceName) → MapImportResult(GameMap Map, IReadOnlyList<NativeSettlement> Settlements)`. **Definition format** (UTF-8 text; `#` begins a comment, blank lines ignored): a header `WIDTH HEIGHT`, then `HEIGHT` rows of `WIDTH` terrain short-names (row-major, `plains` → `model.tile.plains`), then any of four **optional, order-independent** overlay sections, each opened by a bracketed header — `[resources]` (rows `X Y resourceShortName [QUANTITY]`, the optional quantity = FreeCol `Resource.quantity` for a finite deposit), `[improvements]` (rows `X Y improvementShortName [MAGNITUDE]` for river/road, magnitude defaulting to the ruleset type's; FreeCol `TileImprovement`), `[rumours]` (rows `X Y`; FreeCol `LostCityRumour` tile item), and `[settlements]` (rows `X Y nationType settlementType capital|regular SIZE [skillUnit]`; FreeCol `IndianSettlement`). Short names are auto-qualified with the section's `model.*` prefix (a fully-qualified id passes through). Every row is bounds- and id-validated (an `InvalidDataException` names the source + 1-based line on any malformed header/row, off-map coordinate, or unknown id). Settlements get ids from 1 in file order. **`FixedMap` now delegates to the importer:** `LoadAmerica` = `ImportAmerica(ruleset).Map`; since the shipped `america.txt` declares **no** overlay sections, importing it yields the identical terrain-only `GameMap` (empty resource/improvement/rumour layers, no settlements) — so `Game.New(mapSource: America)` decorates exactly as before and the America game stays **byte-identical** (its rivers/resources/natives are still laid by the game-start generators; the `MapImportResult.Settlements` list is now installed by `Game.New` — see the next bullet — but is empty for `america.txt`, so nothing changes for it). A second embedded map, `example-overlays.txt` (6×5), declares all four overlays and is imported via the internal `FixedMap.ImportExampleOverlays` purely to exercise the importer end-to-end. **Faithful-subset scope** (documented deferrals): river **connection styling**, tile **ownership without a settlement**, **European colonies/units**, and the **binary** FreeCol `.fsm` container (we read our extracted text form — see `PROVENANCE.md`) are not imported. (Per-tile **region ids** and **player start positions** were previously-deferred kinds — **now imported**, see the next two bullets; the binary Colonization **`.MP`** container is **now read** too — see the `.MP` bullet below.) **No save bump** (the importer produces an in-memory `GameMap`; persistence is unchanged), **byte-identical default** (the America + Random paths are untouched).
- **Imported native settlements installed into `Game.New` (follow-up to `86d3c9wwk`):** `Game.New` now loads a fixed map through `FixedMap.TryImport` (the full `MapImportResult`) rather than `TryLoad` (terrain only), so it keeps the imported `Settlements` list. **Branch on whether the map declared any:** if `importedSettlements.Count > 0`, those exact settlements (the importer-assigned ids-from-1, plus position/nation/type/capital/size/skill) are **installed verbatim** and the **procedural `NativeSettlementGenerator.Place` is skipped entirely** for that map — the scenario author placed the natives. They are finished exactly as generated ones are: `NativeSettlementGenerator.AssignWantedGoodsTo(importedSettlements, ruleset, nativeRandom)` gives each its wanted goods (drawn on the **native stream**, `NativeStreamId` — never stream 0), and the existing post-placement steps then run unchanged on `game._nativeSettlements` (so imported villages get `ClaimNativeLand`, brave garrisons, and their nations become `PlayerType.Native` players via `SpawnRivalsAndNatives`). If the list is empty (the shipped terrain-only `america.txt`, and **every** `Random` world, whose `TryImport` returns `null` → empty list), the original `else` branch runs `NativeSettlementGenerator.Place(...)` exactly as before — so the **default and America games are byte-identical** (ADR-006/009; **no save bump** — the default map is unchanged byte-for-byte). A **test-only** `Game.New(..., MapImportResult? importOverride = null)` seam lets a test drive a `[settlements]`-declaring scenario map through this real install path without shipping it as a `MapSource`; it is `null` in normal play, so production America/Random are unaffected. *Note:* imported settlements are installed **after** the human's coastal start is chosen and are **not** excluded from it (the scenario author owns placement) — a hand-made map should keep its villages clear of the player's likely landfall, as the example/test maps do.
- **Imported player starts — `[starts]` (map-importer follow-up, extends `86d3c9wwk`):** the importer parses an optional, order-independent **`[starts]`** section — rows `human X Y` and/or `ref X Y` (each at most once; either may be omitted). They flow out of the importer on `MapImportResult.HumanStart`/`RefEntry` (both `Position?`, null when undeclared), mirroring FreeCol fixing a saved scenario's `Player.entryTile` (the human's landing) and `ourREF.setEntryTile` (the REF arrival). **`Game.New` honours them deterministically (no RNG):** `start = imported?.HumanStart ?? <coastal heuristic>` and `SetRefEntryTile(imported?.RefEntry ?? NearestWaterTile(start))`. A fixed human start places the starting units there (and its free neighbours) **instead of** the temperate-coastal pick; a fixed REF tile is where the King's fleet lands on independence (persisted via the existing `RefEntryTile` save field — **no new save field, no bump**). Both are skipped when undeclared, so the shipped `america.txt` and every Random world keep the heuristic result — **byte-identical** (ADR-006/009). Validation: an off-map or duplicate start row is an `InvalidDataException` naming the source + line. *Note:* a fixed human start is **not** excluded from native/LCR placement (the scenario author owns the layout) — a hand-made map should keep its start clear, as the test map does.
- **Imported region layer — `[regions]` (map-importer follow-up, extends `86d3c9wwk`):** the importer parses an optional **`[regions]`** section carrying a complete region layer, mirroring FreeCol `FreeColMapLoader` importing each saved tile's `Region` (`tile.setRegion`) rather than re-deriving it. Two row kinds, freely interleaved: a **declaration** `region ID TYPE [SCORE [KEY [PARENT]]]` (ids dense from 0 in order, so `Region.Id` indexes the table; `TYPE` ∈ `RegionType` names; `KEY` a `model.region.*` key or `-` for none; `PARENT` an already-declared id) and a **tile assignment** `X Y REGION_ID` (referencing a declared id). **Every in-bounds tile must be assigned** — an unassigned tile, an unknown type, a non-dense first id, an undeclared tile id, or a forward parent reference is an `InvalidDataException`. The parsed layer flows out on the imported `GameMap` (built with the importer's `regionIds`/`regions`). **`Game.New` re-installs it over the decorate pass:** `MapGenerator.DecorateFixedMap` always re-derives regions from terrain (`RegionGenerator.Assign`), so when `imported.Map.Regions.Count > 0` we re-apply the imported table + per-tile ids onto the decorated map via `GameMap.SetRegions` (RNG-free; row-major `int[]` rebuilt from `AllPositions().Select(RegionIdAt)`). A map declaring no `[regions]` (the shipped `america.txt`, every Random world) keeps the generator-derived regions — **byte-identical, no save bump** (the region layer persists in the existing v35 format; an imported layer simply serialises its own ids). *Faithful-subset note:* the imported region's discovery fields start unset (a scenario doesn't pre-discover regions); region **discovery** then runs on the imported layer exactly as on a generated one.
- **Colonization `.MP` import (`86d3fpxjc`, FreeCol `server/generator/ColonizationMapLoader.java` ported verbatim):** `MapImporter.ImportColonization(Stream, ruleset, sourceName)` reads the original game's binary map container; `MapImporter.ImportFile(path, ruleset)` dispatches by extension (`.mp` case-insensitive → binary, anything else → the text `Import`) — the seam the New-Game import UI calls. **Format:** a 6-byte header (width at byte 0, height at byte 2 — read as **UInt16 LE**, identical to FreeCol's signed-byte read for every file FreeCol can load and additionally correct for widths > 127, a documented port improvement; bytes 4–5 fixed/ignored), then `width×height` terrain bytes — the first of the file's **three** same-size layers; FreeCol reads only layer 1 and so do we (layers 2–3 + any trailing bytes are ignored). **Decode (FreeCol L162-194):** `terrain = b & 0b11111`, `overlay = b >> 5`; a terrain code < 27 maps through the verbatim 27-entry `tiletypes` table (0–7 tundra…swamp, 8–15 **and** 16–23 the same eight forests — FreeCol's duplicated block, kept as-is; 24–26 arctic/ocean/highSeas), each `Qualify`'d to `model.tile.*` and resolved against the ruleset; a code ≥ 27 has no base type and takes overlay 1/3 → `hills`, 5/7 → `mountains`. Overlay 2/3/6/7 lays `model.improvement.river` `with { Magnitude = overlay <= 3 ? 1 : 2 }` (minor/major; **no connection styling** — FreeCol's own loader leaves connections a `//TODO`). Result: `MapImportResult(map, [], null, null)` — **exactly FreeCol's subset** (terrain + river magnitude; the format carries no bonuses/rumours/settlements/starts), so `Game.New`'s generators decorate it like any terrain-only import. **Documented deviation:** a code ≥ 27 whose overlay is not 1/3/5/7 makes FreeCol silently reuse the *previous* tile's type (NPE on tile 0) — a latent bug; we throw a clean `InvalidDataException` naming the source + tile. Truncated header/layer and zero dimensions are errors too. Deterministic, RNG-free (ADR-009), engine-free (ADR-006). **Licensing:** the loader is a GPL-v2 FreeCol port (fine); we never ship a real original-game `.MP` — test fixtures are synthesized byte arrays.
- **Mountain & hill ranges:** `MapGenerator.MakeMountains(ruleset, terrain, land, w, h, IGameRandom)` ports FreeCol `TerrainGenerator.createMountains`. It collects the land tiles, deterministically Fisher–Yates-shuffles them (private `Shuffle`, FreeCol `RandomUtils.randomShuffle`), and runs the two passes described in §2 (walked ranges to a `½·landCount/MountainNumber` budget with `maxLength = max(w,h)/10`; then a 25/75 mountain/hill sprinkle for the other half). Constants `MountainNumber = 10` (FreeCol `model.option.mountainNumber` classic default) and `RandomHillsRatio = 0.5`. The old `RollAltitude` is now `RollLowlandAltitude` (always 1–3). **This pass draws RNG**, so it reorders the stream-0 draw sequence — a deliberate map-gen change for this item (ADR-009 allows it; the goldens + downstream seed-pinned tests were regenerated/retargeted accordingly). Resources move to a dedicated post-terrain pass (FreeCol "add bonuses last") so a retyped mountain tile gets mountain resources, not a stale lowland one.
- **High-seas band:** `MapGenerator.ResetHighSeas` (pure, RNG-free), a port of FreeCol `Map.resetHighSeas(distToLandFromHighSeas, maxDistanceToEdge)` with the classic spec values `DistanceToHighSea = 4` / `MaxDistanceToEdge = 10`: it resets every high-seas tile to ocean, then for each row walks the contiguous ocean strip inward from each east/west edge (up to `MaxDistanceToEdge` columns, stopping at the first land) and promotes an ocean tile to high seas when no land lies within `DistanceToHighSea` (8-dir Chebyshev), with a furthest-from-land fallback so each side always has at least one exit. **It runs after `MakeMountains` and before the resource pass, and consumes no RNG**, so it never needs to drop a resource (none exist yet) — a high-seas tile simply never receives one (the resource pass skips water, which has no resource table). **No save bump:** high seas is a terrain `Type`, not a save-format field — a value change inside the existing terrain layer, like lake tagging; old saves keep their terrain, new games get the band. Region assignment is unaffected (it doesn't distinguish ocean subtypes).
- **World-size options:** `WorldSizeOptions` (static, GameLogic) holds the immutable `WorldSize(Name, Width, Height)` and `LandMass(Name, Fraction)` preset lists + the default indices; no save change (map dimensions persist since save v2). Presentation: `NewGameDialog` (programmatic overlay, ADR-006) lets the player pick before starting and forwards the choice via `GameController.PendingWorldSize`/`PendingLandMass` (statics that survive the menu→game scene change, like `PendingLoadPath`) into `GameController.StartNewGame(seed, size, landMass)` → `Game.New`. The parameterless `StartNewGame(seed)` (tests/goldens) uses the shipped defaults, so it is unchanged.
- **Landmass styles (`86d3drn76`):** `LandStyle` (enum `Continent=0`/`Archipelago=1`/`Islands=2`, in `WorldSizeOptions.cs`) ports FreeCol `MapGeneratorOptions.LAND_GENERATOR_*`. `MapGenerator.Generate(..., landMassFraction, landStyle = LandStyle.Continent)` switches: `Continent` → the unchanged `GrowContinent` (byte-identical default); else `GrowSeparateMasses(width, height, random, landMassFraction, style)`, which grows multiple unconnected blobs via `AddLandMass` (a port of FreeCol `LandMap.addLandMass`: pick a sea seed with no adjacent land inside the `LandMarginX`/`LandMarginY` margin, then random-frontier-grow to a `[minSize, maxSize]` blob whose tiles never touch another mass, discarding an undersized blob). Archipelago = 5 islands at `targetLand·10/100 ± 5` then the islands fill; Islands = `25..25+rand(50)`-tile islands to the land budget; both bounded by a `width·height` attempt guard. `Game.New` gains `landStyle = LandStyle.Continent` (last param, so existing calls/goldens are unchanged) and forwards it to `Generate` on the random path only (a fixed `mapSource` ignores it). `WorldSizeOptions.LandStyles`/`DefaultLandStyleIndex`/`DefaultLandStyle` ("data not code", like the size/land presets). Presentation: `NewGameDialog`'s **Landmass** dropdown (Continent/Archipelago/Islands, disabled for a fixed map) forwards the pick via `GameController.PendingLandStyle` → `StartNewGame(..., landStyle)` → `Game.New`. **No save change** (land shape persists as terrain ids); **byte-identical default** (Continent = the historical generator).
- **Bonus resource placement (`86d3c9wbp`):** the resource pass (after `ResetHighSeas`) rolls per tile from its final terrain's weighted table (`PickWeightedResource`) — **land** at `LandBonusChance = 0.10` (FreeCol `BONUS_NUMBER`), **water** only when `LandNeighbours(tile) > WaterResourceMinLandNeighbours (=1)` at `1 / (WaterResourceOddsBase (=10) − adjacentLand)` odds (FreeCol `perhapsAddBonus`). A tile whose terrain has no resource table draws nothing; open ocean (≤1 land neighbour) draws nothing. **Draws RNG → a deliberate stream-0 reorder** for this item (goldens regenerated; one downstream seed-pinned monarch idle-test retargeted). `GameMap.Resources` stays `Position → id`; the constants are hardcoded from the spec for now (read `bonusNumber` from the map-gen options later, with `mountainNumber`/high-seas).
- **Per-resource quantity (`86d3c9wbp`, v46):** `ResourceType` parses `minimum-value`/`maximum-value` (→ `MinValue`/`MaxValue`; `HasQuantityRange` ⇔ `MaxValue > 0`, the inverse of FreeCol's `limitless`); `ResourceType.RollQuantity(IGameRandom)` returns `MinValue + rng.Next(MaxValue − MinValue + 1)` (FreeCol `RandomRange`), 0 for a limitless type. `GameMap` carries a sparse `Position → int` quantity layer (`ResourceQuantityAt`/`ResourceQuantities`/`SetResourceQuantity`, ctor-restored like the resource/rumour layers). `Game.RollResourceQuantities(seed)` walks the placed resources in row-major order and stamps a rolled amount on each finite one, drawing from a reserved stream (`ResourceQuantityStreamId = 102`) so stream 0 is untouched. Save field `SavedResourceQuantity` (`ResourceQuantities`, v46, omitted when none). **`Game.New` now calls `RollResourceQuantities(seed)` right after `MapGenerator.Generate`**, so a placed finite deposit carries a quantity from turn 1. The reserved stream means no stream-0 reorder (the human's draw sequence is byte-stable; soak unaffected), but a default save now emits a `ResourceQuantities` token, so the L4 map golden + soak baseline were regenerated this wave.
- **Coastal fish bonus:** `Game.TileYieldPotential` (in the tile-yield cluster of `Game.cs`) adds `CoastalFishBonus = 2` to a fish potential when `IsCoastalWater(tile)` — a private helper that returns true for water that isn't `model.tile.highSeas` and has `> CoastalLandNeighboursRequired (=2)` land neighbours (`tile.Neighbours().Count(n => InBounds(n) && !TerrainAt(n).IsWater)`). Pure (terrain + adjacency), RNG-free, no stored state; ports FreeCol `TerrainGenerator.perhapsAddBonus` / `fishBonusLand`. The **river-mouth +1** (`RiverMouthFishBonus`, `IsRiverMouthWater`) stacks on top of this — full detail in [rivers-tile-improvements](rivers-tile-improvements.md).
- **Regions:** `RegionType` (enum `Ocean=0`/`Land=1`/`Mountain=2`/`River=3`/`Lake=4`/`Coast=5`/`Desert=6`, serialized by ordinal — `River` **produced** per connected river system since `86d3fpxnm`, `Lake` produced for enclosed water, `Coast`/`Desert` **reserved-only** exactly as FreeCol, which declares but never instantiates them), `Region` (record: `Id`, `Type`, `ScoreValue`, `Key?`, `ParentId?`, **`DiscoveredBy?`, `Name?`, `DiscoveredInTurn?`**, **`Bounds?`** — `Id` equals the index into `GameMap.Regions`; fixed regions carry a `model.region.*` key, dynamic land/mountain/river regions a null key; ocean quadrants link to their parent ocean via `ParentId`; the three discovery fields are null until a player discovers the region; `Bounds` (`RegionBounds(X, Y, Width, Height)`, a half-open box with a `Contains(Position)` test — FreeCol `ServerRegion.bounds`) is carried **only** by the nine virtual thirds regions and is null for every tile-bearing one). `Region.IsDiscoverable` (no `DiscoveredBy` yet **and** ((Land/Mountain/**River** with a null `Key`) **or** the Pacific key — FreeCol's `ServerRegion(game, RegionType.RIVER)` ctor sets `discoverable = true`)) and `Region.IsDiscovered` (`DiscoveredBy != null`) encode FreeCol `ServerRegion` discoverability. `GameMap` holds a dense row-major `int[]` region layer (`RegionIdAt` → id or `GameMap.NoRegion`; - **Isometric (diamond) tile picking (`86d3f675b`):** `MapView.TileAt(Vector2 local)` is the exact inverse of `TileCentre` and a **true point-in-diamond** pick — not a rectangular bounding box. Inverting the forward projection gives fractional grid coordinates `x = (u+v)/2`, `y = (v−u)/2` where `u = localX/64`, `v = localY/32`; rounding each (`Mathf.RoundToInt`, half-away-from-zero) selects the tile whose diamond contains the point. Independent rounding in this rotated basis is **provably** a point-in-diamond test: the region rounding to `(X,Y)` is `|x−X| ≤ ½ ∧ |y−Y| ≤ ½`, which maps to the drawn diamond (corners at local offsets `(±64,0)`/`(0,±32)`) — verified exhaustively (round-trip for every tile + ~100k interior samples, all self; every edge/corner crossing resolves to the expected neighbour). **The wonky-click bug was *not* the math** — it was the *input plumbing*: both click handlers in `GameController._UnhandledInput` read `_mapView.GetLocalMousePosition()` (the **live** OS cursor, polled when the buffered event is dispatched), so a cursor that drifted between button-down and dispatch (camera pan, wheel zoom, or buffered input) picked a different tile than the one clicked. Fixed by picking from the **event's own** `Position`: new `MapView.TileAtScreen(Vector2 viewportPosition)` maps the screen-space event point through `GetGlobalTransformWithCanvas().AffineInverse()` (which folds in the `Camera2D` zoom/pan) into node-local space, then `TileAt`. `HandleTileClick`/`HandleRightClick` now pass `mouseEvent.Position`; `HandleRightClick(Vector2? viewportPosition = null)` falls back to the live cursor only when driven directly (the L3 stack-menu test). Pure presentation (ADR-006); no save change.
